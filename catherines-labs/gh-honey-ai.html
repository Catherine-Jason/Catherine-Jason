Honey-AI: LLM Injection Honeypot

I built Honey-AI as a local research honeypot for LLM prompt injection testing. The goal was to capture suspicious prompts, score them in a repeatable way, store the activity, and give myself a simple monitoring workflow that feels familiar from a SOC analyst point of view.

Overview / What I Built

The stack combines a FastAPI backend, a local Ollama model, SQLite logging, a Streamlit dashboard, and a text report generator. A prompt is submitted to the /chat endpoint, sent to a local OllamaOllama lets me run LLMs locally, which keeps this project in a contained test environment instead of depending on a public hosted model. instance running llama3.2:1b, then reviewed by a keyword-based risk scoringRisk scoring is a simple way to turn suspicious language into a repeatable number so I can sort lower concern prompts from higher priority ones. function before it is logged.

I designed it to do two things at the same time. First, it gives me a safe place to study how users might try prompt injectionPrompt injection is when someone tries to manipulate an AI system with instructions meant to override its normal rules or expose restricted information. against a local LLM. Second, it creates a monitoring trail that I can review through raw logs, a SQLiteSQLite is a lightweight file-based database. It is a practical way to keep structured event history without deploying a separate database server. database, a StreamlitStreamlit is a Python framework for quick dashboards. Here it turns stored event data into charts, counts, and review tables for fast triage. dashboard, and a text summary report.

  • FastAPI backend that accepts prompts and forwards them to a local Ollama llama3.2:1b model
  • Keyword-based scoring logic that detects common prompt override and jailbreak language
  • Dual logging to plain text files and a SQLite database for both quick review and structured analysis
  • Streamlit dashboard with summary metrics, recent events, and basic trend views
  • Plain-text reporting that summarizes prompt counts, high-risk events, critical events, and average risk score

Architecture Walkthrough

The project flow is intentionally simple and easy to audit. A client sends a prompt to the FastAPI /chat endpoint. The backend forwards that content to Ollama, scores the prompt for injection indicators, writes the response and risk metadata to the standard chat log, flags higher risk events into a separate security log, stores the event in SQLite, and then exposes that history to both the dashboard and the report generator.

  1. Client request: a user submits a prompt to the local chat endpoint.
  2. Model proxy: FastAPI sends the prompt to the local Ollama generate API.
  3. Risk review: the backend checks the prompt for prompt injection phrases and assigns a score plus a severity label.
  4. Log handling: every event is written to chat_log.txt, and higher-risk events are copied to security_events.txt.
  5. Structured storage: the same event is stored in logs/honey_ai.db so it can be queried later.
  6. Analyst visibility: the Streamlit dashboard uses the stored data for metrics, daily counts, and recent event review.
  7. Reporting: the report generator creates a plain-text summary that can be saved with the rest of the project notes.

Risk Scoring Methodology

The current logic is intentionally lightweight. Each suspicious keyword pattern adds 25 points, and the total score is capped at 100. That makes the scoring easy to explain, easy to test, and easy to tune later if I want to expand the pattern list.

Pattern checked Why it matters Score impact
ignore previous instructions Classic attempt to override the existing prompt or safety context +25
reveal system prompt Direct effort to exfiltrate hidden model instructions +25
developer mode Common phrasing used to push a model into a less restricted state +25
jailbreak Explicit attempt to bypass guardrails or normal controls +25
  • Low: 0 to 24
  • Medium: 25 to 49
  • High: 50 to 74
  • Critical: 75 to 100
  • Security event logging threshold: prompts scoring 50 or higher are written to security_events.txt

Sample SOC Findings / Analyst Workflow

Because the project is still in a fresh-install state, I am not presenting live incident totals as if they already happened. Right now the report shows zero recorded prompts, so this section is a sample analyst walkthrough based on how the monitoring stack is designed to work once prompts start coming in.

  • Prompt override attempts: I would watch for phrases that try to replace the original tasking, especially language like “ignore previous instructions.”
  • System prompt exfiltration: Requests to reveal hidden instructions would be reviewed as attempts to expose internal control logic.
  • Safety bypass attempts: Phrases like “developer mode” would be grouped as attempts to relax normal restrictions.
  • Jailbreak language: Direct use of jailbreak phrasing would be treated as a strong sign that the user is intentionally testing or bypassing controls.

In a daily workflow, I would start with the dashboard summary cards to see total prompt volume, high-risk prompt volume, average risk score, and critical event count. Then I would move into the recent events table to review the exact prompt text, score, and trend context. High events would tell me the prompt contained multiple concerning indicators. Critical events would tell me the prompt stacked enough suspicious patterns that it deserves immediate review first. As real prompts are submitted, the dashboard and report will populate with actual findings that can support triage notes or future tuning.

Security & Safety Note

This project runs against a local Ollama instance and is meant for research and education. It does not expose a real production system, and it should always be operated in an isolated local environment so testing stays contained and does not affect live assets.
